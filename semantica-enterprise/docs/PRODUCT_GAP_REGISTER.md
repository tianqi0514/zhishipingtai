# 产品缺口登记簿

## 初始审计与处置结果

| 编号 | 级别 | 缺口 | 业务影响 | 处置状态 |
|---|---|---|---|---|
| PG-001 | P1 | 现有数据是技术验收集，组织仅 2 个、用户仅 1 个 | 无法证明集团层级、角色和空间隔离可交付 | **已关闭**：建立 14 个组织节点、8 类账号、5 个权限边界不同的空间及显式拒绝；由真实账号/API/浏览器共同验收 |
| PG-002 | P1 | 现有产品文档没有机器可验证的集团业务标准答案 | 测试只能判断接口成功，无法证明回答正确 | **已关闭**：建立 29 份制度、产品、采购多模态资料、14 张双方言经营表和固定数值/证据断言 |
| PG-003 | P1 | 应用反馈转治理已实现，但治理发布后重新评测的业务状态与入口尚未证明 | 应用质量闭环可能停在“已转治理” | **已关闭**：反馈进入治理后为“待处理”，治理发布后为“待验证”；仅匹配场景且门禁通过的真实 Evaluation Run 可确认“已解决” |
| PG-004 | P2 | 工作台显示指标和快捷操作，但没有按系统真实状态给首次管理员唯一下一步 | 新管理员可能不知道先建组织、空间还是模型 | **已关闭**：工作台按组织、模型、空间、文档/任务真实状态计算一个“建议下一步”，不使用静态文案 |
| PG-005 | P2 | 数据源同步任务、文档版本和加工任务之间的页面跳转需逐项验证 | 用户难以判断“同步成功”和“可检索” | **待最终浏览器回归**：后台关联对象和业务状态已实现，需逐个来源核对页面跳转 |
| PG-006 | P2 | `process_knowledge` 等任务类型仍在工作台直接显示英文内部名 | 普通用户不易理解 | **已关闭**：统一显示“解析文档、加工知识、同步数据源、发布人工治理、运行知识分析”等业务名称 |
| PG-007 | P2 | 历史失败任务保留在工作台但缺少聚合原因/下一步判断 | 管理员无法快速判断是否需处理 | 待运营页面验证 |
| PG-008 | P2 | 应用正式运行 API 当前以场景检索为主，场景化 Agent 问答能力需确认产品定位 | 应用构建可能只覆盖检索型应用 | **已明确边界**：应用 Runtime 提供版本化场景检索；完整 Agent 对话使用平台会话 API/DSH，接入手册和开发者指南不再把检索冒充 Agent |
| PG-009 | P3 | DSH 合约测试正确命令依赖 Agent Runtime/tsx 环境，README 容易被误用 | 交付人员会得到假失败 | **已关闭**：README 和 DSH 文档提供容器内 `npm test` 入口，锁定版本合约实测 15/15 |

本表在每轮回归后更新“根因、修复提交、验证证据和遗留风险”。P0/P1 未关闭前不得宣布完成。
