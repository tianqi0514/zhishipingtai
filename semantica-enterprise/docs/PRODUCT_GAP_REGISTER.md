# 产品缺口登记簿

## 初始审计与处置结果

| 编号 | 级别 | 缺口 | 业务影响 | 处置状态 |
|---|---|---|---|---|
| PG-001 | P1 | 现有数据是技术验收集，组织仅 2 个、用户仅 1 个 | 无法证明集团层级、角色和空间隔离可交付 | **已关闭**：建立 14 个组织节点、8 类账号、5 个权限边界不同的空间及显式拒绝；由真实账号/API/浏览器共同验收 |
| PG-002 | P1 | 现有产品文档没有机器可验证的集团业务标准答案 | 测试只能判断接口成功，无法证明回答正确 | **已关闭**：建立 29 份制度、产品、采购多模态资料、14 张双方言经营表和固定数值/证据断言 |
| PG-003 | P1 | 应用反馈转治理已实现，但治理发布后重新评测的业务状态与入口尚未证明 | 应用质量闭环可能停在“已转治理” | **已关闭**：反馈进入治理后为“待处理”，治理发布后为“待验证”；仅匹配场景且门禁通过的真实 Evaluation Run 可确认“已解决” |
| PG-004 | P2 | 工作台显示指标和快捷操作，但没有按系统真实状态给首次管理员唯一下一步 | 新管理员可能不知道先建组织、空间还是模型 | **已关闭**：工作台按组织、模型、空间、文档/任务真实状态计算一个“建议下一步”，不使用静态文案 |
| PG-005 | P2 | 数据源同步任务、文档版本和加工任务之间的页面跳转需逐项验证 | 用户难以判断“同步成功”和“可检索” | **已关闭**：数据源同步详情、任务详情、文档版本、元素/Chunk/画像和当前索引状态已通过 API、增量脚本与浏览器联合回归；失败同步提供真实错误和重试 |
| PG-006 | P2 | `process_knowledge` 等任务类型仍在工作台直接显示英文内部名 | 普通用户不易理解 | **已关闭**：统一显示“解析文档、加工知识、同步数据源、发布人工治理、运行知识分析”等业务名称 |
| PG-007 | P2 | 历史失败任务保留在工作台但缺少聚合原因/下一步判断 | 管理员无法快速判断是否需处理 | **已关闭**：工作台按真实失败数量给出“处理异常任务”，任务中心展示业务任务名、错误、步骤和重试；运营中心汇总失败任务与能力异常 |
| PG-008 | P2 | 应用正式运行 API 当前以场景检索为主，场景化 Agent 问答能力需确认产品定位 | 应用构建可能只覆盖检索型应用 | **已明确边界**：应用 Runtime 提供版本化场景检索；完整 Agent 对话使用平台会话 API/DSH，接入手册和开发者指南不再把检索冒充 Agent |
| PG-009 | P3 | DSH 合约测试正确命令依赖 Agent Runtime/tsx 环境，README 容易被误用 | 交付人员会得到假失败 | **已关闭**：README 和 DSH 文档提供容器内 `npm test` 入口，锁定版本合约最终实测 16/16 |
| PG-010 | P2 | 审计日志默认展示内部动作码、UUID 与原始 JSON | 集团管理员难以理解，也不应在主列表暴露内部标识 | **已关闭**：列表改为中文业务操作、业务对象和人员姓名；内部标识默认不展示，业务详情按需打开 |
| PG-011 | P1 | 数值问题与统计口径解释问题可能走错证据通道 | 数值可能来自文档描述，或口径问题被无意义地查询数据库 | **已关闭**：确定性 Query Policy 将数值、定义和混合问题分流；FastAPI 强制激活 Metric Contract；DSH 16 项与真实组合问答通过 |
| PG-012 | P1 | 引用编号可能被模型按答案顺序重排 | 点击引用可能打开错误片段 | **已关闭**：引用编号作为不可变片段外键从检索层发放，回答完成前校验；浏览器 `[1]` 与 `【数据1】` 均定位真实来源 |

## 2026-09-02 最终结论

P0/P1 缺口均已关闭。P2/P3 中本轮范围内的业务断点均已修复或形成明确产品边界；Google Drive、OneDrive/SharePoint、Snowflake、新运维中心和大规模性能优化依照用户确定的范围不作为本轮完成条件。完整证据见 `FULL_PLATFORM_VALIDATION_20260902.md`。

本表在每轮回归后更新“根因、修复提交、验证证据和遗留风险”。P0/P1 未关闭前不得宣布完成。
