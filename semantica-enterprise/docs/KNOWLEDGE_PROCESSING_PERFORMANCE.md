# 知识加工性能与模型调用策略

## 背景

知识加工并不等同于文件解析。文件解析完成后，平台还会依次执行切片、文档画像、语义抽取、知识治理、图谱发布和检索索引发布。其中，文档画像与语义抽取会调用所配置的大模型，实际耗时受模型响应速度、超时和重试策略影响。

2026-09-03 对 `传神AI配音案例分析.docx` 的问题复盘显示：文件只有 2,311 个正文字符，但 DOCX 解析后形成了 26 个结构元素。旧实现按每个 Chunk 串行调用一次 Kimi K3，共发起 26 次语义抽取请求；其中 4 次超时，整段知识加工耗时 20 分 53 秒。

## 优化后的处理方式

平台仍保留原始 ContentElement 和 Chunk，不改变检索、页码、结构路径和引用粒度。仅在语义抽取的模型调用边界内，将相邻短 Chunk 组合成有上限的批次：

1. 按原始顺序组合相邻短 Chunk。
2. 每批同时受字符数和 Chunk 数量上限约束。
3. 按模型配置的并发数并行调用，平台硬限制最大并发为 8。
4. 模型返回的实体、关系和事件必须重新定位到包含原文证据的原始 Chunk。
5. 无法定位原文证据的项目不会写入知识库，避免批处理削弱 Provenance。
6. 单个批次失败只影响该批次，其他成功结果仍可治理和发布。

默认策略：

| 配置 | 默认值 | 说明 |
|---|---:|---|
| `batch_chars` | 根据切片长度计算，当前通常为 2,400 | 单次抽取请求的目标字符上限 |
| `batch_max_chunks` | 12 | 单次抽取请求最多包含的原始 Chunk 数 |
| 模型 `concurrency` | 来自模型配置 | 同时执行的模型请求数，平台限制为 1–8 |
| 模型 `timeout` | 来自模型配置 | 单次模型请求超时 |
| 模型 `retry` / `max_retries` | 来自模型配置 | OpenAI 兼容客户端的自动重试次数 |

管理员可以在“配置中心 → 加工策略 → 语义抽取 → 附加参数”中设置 `batch_chars` 和 `batch_max_chunks`，在“配置中心 → 模型配置”中调整并发、超时和重试。参数调整会影响吞吐、模型稳定性和单次响应大小，修改后应使用代表性文档回归。

## 可观测指标

知识加工任务的 `semantic_extract` 步骤记录：

- `chunks`：原始检索 Chunk 数。
- `model_chunks`：成功完成模型抽取的原始 Chunk 数。
- `reused_chunks`：增量更新时复用既有抽取结果的 Chunk 数。
- `failed_chunks`：模型请求失败影响的原始 Chunk 数。
- `model_requests`：实际模型请求批次数。
- `successful_model_requests`：成功批次数。
- `batch_target_chars`、`batch_max_chunks` 和 `concurrency`：本次实际运行参数。
- `unanchored_items`：模型输出中因无法定位原文证据而被拒绝的项目数。

步骤出现部分失败时状态为 `partial`，仍会记录真实 `finished_at`，任务详情不会再表现为一直运行。

## 真实回归结果

2026-09-03 使用同一份 DOCX、同一 Kimi K3 配置和同一知识空间重新上传验证：

| 指标 | 优化前 | 优化后 |
|---|---:|---:|
| 原始 Chunk | 26 | 26 |
| 语义抽取模型请求 | 26 | 3 |
| 知识加工总耗时 | 20 分 53 秒 | 5 分 15 秒 |
| 抽取成功的原始 Chunk | 22 | 24 |
| 抽取超时影响的 Chunk | 4 | 2 |
| 实体 / 关系 / 事件 | 未作为本次基线重点 | 20 / 16 / 2 |
| 无法定位原文证据 | 未记录 | 0 |

优化后耗时降低约 75%。剩余主要耗时来自云端 Kimi K3：文档画像约 1 分 58 秒，语义抽取约 2 分 36 秒，其中一个批次在配置的自动重试后仍超时。平台会保留确定性画像、成功抽取结果、全文/向量索引，并以 Warning 明确标记降级，不会把失败伪装为成功。

## 模型选型建议

Kimi K3 可以继续用于默认问答和高质量治理，但它是偏推理型模型，批量抽取的延迟会明显高于快速结构化输出模型。生产部署建议将“问答模型”和“加工模型”拆成两份独立模型配置：

- 问答使用推理质量更高的模型。
- 文档画像和语义抽取使用支持稳定 JSON 输出、低延迟和较高并发的模型。
- 向量仍使用本地 BGE，不依赖 Kimi。

平台不硬编码具体供应商；两个模型都通过现有模型配置和策略 CRUD 选择。
