## 4. 与客户样本的差距

| 维度 | 客户正式下发件 | 本次生成稿 | 判断 |
|---|---:|---:|---|
| 正文字符 | 10,849 | 26,683 | 生成稿为 245.9%，明显冗长 |
| 非空段落 | 156 | 456 | 章节和说明重复 |
| 页数 | 29 页 | DOCX 渲染 27 页；PDF 31 页 | 页数接近不等于内容质量接近 |
| 页面尺寸 | A4 | Letter | 未套用正式模板 |
| 一级章节 | 9 章，各一次 | 第一章一次，第二至九章各两次 | 多轮中间稿与最终稿一起写入 |
| 重复长句 | 未发现系统性重复 | 130 条，29.7% | 不可作为正式稿 |
| 模型工作草稿 | 无 | 81 处 | 英文分析过程泄漏到正文 |
| 平台过程说明 | 无 | 25 处 | “工具调用、图谱为空”等不应进入正文 |
| Plate 引用节点 | 不适用 | 326 个 | 编辑器内部引用结构存在 |
| DOCX 正文可见引用 | 客户正文采用可读依据表达 | 0 个 | 导出器丢失正文内引用 |
| 测算可信块 | 客户推演依据单独成册 | 0 个 `computed_metric` | 数值退化为普通文字 |
| 推演可信块 | 客户推演依据单独成册 | 0 个 `inference_conclusion` | 结论未绑定推演运行 |
| 独立推演依据 | 23 页独立文档 | 只有尾部原始依据清单 | 尚未形成客户需要的双产物 |

本次实际质量缺陷：

1. 生成文本混入诸如 `Let me ...`、`I have ...`、检索结果统计和图谱空结果说明，这些属于 Agent 工作过程，不是正式正文。
2. 九次章节调用返回的中间草稿与最终修订稿被同时拼接，造成第二章至第九章重复。
3. 生成稿比客户下发件长 145.9%，但主要增加的是重复、元说明和工程信息，并非更完整的业务内容。
4. 引用在 Plate 页面内可点击，但 DOCX 导出没有渲染正文引用编号、脚注或尾注，只在文末追加 72 条工程化来源路径。
5. 文末来源包含 YAML 文件名、内部类型等工程信息，不是业务人员可读的“法规条款—数据表行—推演步骤”证据说明。
6. 数值结果和推演结论虽然后台来源正确，写入正文后却变成普通文本，无法利用 `ComputationRun` 和 `InferenceRun` 做局部失效、重算和审计。
7. 导出采用 Letter 页面，缺少客户样本中的 A4、公文标题、文号、签发、版记、正式字体和对应分页控制。
8. 客户样本包含独立的推演依据说明；当前系统只导出一份正文和简短依据清单。
9. 当前“执行审校”会对上述文稿返回“审校通过，可以生成正式文件”，说明审校规则仍是功能完整性检查，没有形成生产质量门禁。
10. 客户 Ontology、Chunks 和 Report Spec 已作为知识材料入库，但没有被导入为可版本化、可校验的 `ScenarioPackage` 契约；盲测仍需测试脚本另外创建章节契约。

## 5. 严格验收结果

通过 12 项：

1. 结果样稿未进入生成输入。
2. 7 份源材料真实解析并发布向量和图谱。
3. 客户数据表事实具有工作表和行级定位。
4. Semantica 规则推演成功。
5. 确定性计算与 Ground Truth 一致。
6. 三套算法方案真实不同。
7. DSH 按九章调用写作和知识工具。
8. 九章结构均有覆盖。
9. 责任单位和时限达到基本可执行门槛。
10. 72 条引用覆盖 7 份来源。
11. 内容保存为 Plate 原生节点。
12. DOCX/PDF/JSON/XLSX 四种格式真实导出。

失败 7 项：

1. 正文体量不在客户样本的 75%—140% 区间。
2. 正文存在模型工作草稿和平台内部执行说明。
3. 一级章节没有保持唯一。
4. 重复长句比例超过 5% 门槛。
5. DOCX 不是 A4。
6. DOCX 正文没有可见引用编号。
7. 确定性计算和推演结论未使用可信业务块。

## 6. 从结果倒推的整改顺序

### P0：先阻止不合格文稿被当作正式成果

1. 增加服务端 `WritingGenerationRun`，一次任务完成材料锁定、事实检查、推演、计算、逐章生成、全局审校和草稿写回；前端不再把 9 次聊天回复直接拼成正式文稿。
2. 每章工具只允许返回严格结构化产物：`section_key`、`title`、`nodes`、`citation_refs`、`metric_refs`、`inference_refs` 和 `warnings`。拒绝自由文本中的工作草稿。
3. DSH 的执行过程只写入 Session Event；最终正文只接受 `structured_final_section`。命中英文工作草稿、工具过程说明或未允许字段时阻断写回并重试一次，仍失败则明确失败。
4. 将当前“执行审校”升级为服务器端发布门禁，至少校验章节唯一、重复率、正文长度、非业务语言、必需责任和时限、引用有效性、可信块完整性、未确认事实和过期绑定。任一硬门槛失败时禁止正式导出。
5. 生成数值和推演结论时，必须插入 `computed_metric`、`inference_conclusion` 等 Plate 业务节点并保存对应运行 ID；模型只负责上下文语言，不得把权威值作为普通字符串写入。
6. 修复 DOCX/PDF 导出：使用 A4 正式模板，将 `knowledge_citation` 渲染为正文引用和脚注/尾注，将业务块渲染为正式文本并保留可审计映射。
7. 同一次任务生成两个关联产物：正式应急处置方案、推演依据说明。二者共同绑定相同的 Release、场景包、事实、规则和计算版本。

### P1：让“从材料到报告”成为用户可操作的一条链

1. 增加场景包导入，把客户 ontology/chunks/report-spec YAML 转换成版本化、可校验、可比较的配置，而不是只作为检索文档。
2. 在妙笔任务内提供“上传材料/选择智库材料”，展示解析、治理、Release 锁定和事实抽取状态；目前只能从平台材料页跳转，用户看不出文档如何进入当前任务。
3. 增加文稿选择与版本切换。当前项目存在多个文稿时页面默认取第一份，缺少明确选择器。
4. 证据栏优先展示业务名称、页码、工作表和行号，原始 YAML、内部版本 UUID 和工具类型放到“技术信息”。
5. 事实确认必须覆盖 Semantica 推导事实本身，不能只确认导出闸门后仍显示 20/21。
6. 上传加工的首轮串行耗时约 7 分 53 秒，主要瓶颈是 `document_profile` 和 `semantic_extract`，尤其三份 YAML；应按媒介和用途路由，配置类 YAML 优先结构化导入，不执行无价值的全文治理与大模型实体抽取。
7. 在没有依赖关系的前提下并行处理材料，并为每阶段设置模型超时、并发和可重试策略。相同文件第二次执行 SHA 复用仅约 0.247 秒，增量复用逻辑已有效。

### P2：用客户样本建立持续质量基线

1. 将本盲测脚本加入发布候选验收；最终样稿继续作为 holdout，只在生成后评分。
2. 增加章节级业务评分：事实正确、职责明确、时限明确、资源缺口一致、引用覆盖、可执行动作和语言正式度。
3. 增加导出渲染回归：A4、标题层级、字体、表格、页眉页脚、文号、版记、分页和正文引用。
4. 增加“事实变化 320 → 400”的局部失效测试，确保仅相关计算、推演和正文块变为 stale，重算后缺口由 180 变为 100。
5. 将 63/100 作为当前真实基线。只有所有 P0 硬门槛通过，才允许页面和报告显示“可正式发布”。

盲测脚本会先写出完整 JSON/Markdown 报告，再在未达到基线时返回非零退出码，便于 CI 和发布流程真正阻断不合格版本。

## 7. 性能结论

首次处理 7 份材料的解析和知识加工串行累计约 472.6 秒。主要耗时不在基础文本解析，而在自动画像与语义抽取：

- 三份 DOCX：约 35—59 秒/份。
- XLSX：约 32 秒，语义抽取占主要部分。
- 三份 YAML：约 86—107 秒/份，画像和语义抽取占主要部分。
- 九章 DSH 写作：约 251.4 秒。

如果按当前串行路径现场从零开始，最小总耗时约 12 分钟，尚未达到客户“材料准备完成后五分钟内形成多方案”的目标。相同材料重新运行时可通过 SHA 复用，7 份合计约 0.247 秒，但生产系统不能只依赖预热数据掩盖首次耗时。

## 9. 当前可用于什么

当前版本适合：

- 验证完整技术链路。
- 演示知识、推演、计算、DSH 和 Plate 的真实集成。
- 作为业务人员继续编辑的初始材料草稿。
- 验证引用、事实、方案和导出数据对象。

当前版本不适合：

- 一键直接生成正式下发件。
- 无人工清理直接对外发布。
- 以当前“审校通过”作为生产质量证明。
- 宣称已达到客户样稿的正式文稿质量。
