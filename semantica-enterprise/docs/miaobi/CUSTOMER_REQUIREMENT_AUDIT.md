# 妙笔客户需求审计

## 结论

客户材料要求的不是通用聊天式写作，而是将预案原文、灾情数据、确定性计算、规则推演和调度结果编排成正式应急方案。正式结果必须区分已知事实、测算值、推导结论与人工决定，并保留来源和版本。地震场景具备可执行的事实、规则、公式、报告结构和样稿；其他六类灾种只有章节级需求，仍需客户确认细化规则和参数，不能按“换标题”验收。

审计材料为用户提供 ZIP 的只读副本。原始附件不进入 Git，也不被修改。

## 客户材料中需要保留的边界

- `minimum_plan_count = 2`，`default_plan_count = 3`，由场景包配置而不是写死在代码。
- 地震等级和资源缺口属于可验证规则与公式，不交给大模型自由生成。
- 响应等级、正式下发和跨级请求属于人工决定。
- YAML 中的本体、Chunks 和报告 Spec 是输入契约来源，需要转为平台版本化对象；不能只塞进提示词。
- 地震以外六类场景缺少足够权威参数，交付时提供独立输入 Schema、章节模板和最小 Fixture，但状态保持“模板待业务确认”。

## 地震场景关键依据

- 州预案规定人口密度达到 200 人每平方公里的地区发生 6.0 级以上、7.0 级以下地震，可初判为重大地震灾害（II 级）。
- 客户推演数据给出震级 6.2、人口密度 305.6。
- 客户报告和推演表给出搜救目标 500 人、当前 320 人；创伤床位目标 330 张、县域 110 张、全域可调用 250 张；帐篷目标 7000 顶、当前 5200 顶。
- 资源数值在客户表个别页签存在口径不一致。例如救护车“当前可用 58”和正文“可调用 46”同时出现。系统必须建立 FactConflict 并要求用户确认，不能静默选值。
